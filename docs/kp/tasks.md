# Задания: КП для салонов + визуалы + демо-сайт

Только салоны. Косметологии — позже.

## Как работать

1. Каждый этап — **новый чат**. Выберите модель из таблицы, скопируйте блок «Промпт» целиком.
2. Источник решений: `docs/kp/brief.md`. Транскрипции не открывать.
3. **Каждый этап обязан прочитать артефакты предыдущего** (список в промпте). Не начинать следующий, пока предыдущий не принят.
4. После этапа: бегло проверить результат → закоммитить (если попросите) → идти дальше.
5. До этапа 5 желательно решить порог базы для «от 50 000 ₽» (см. бриф). Если не решено — оставить формулировку из брифа.

## Цепочка и модели

```
1 Текст КП  →  2 Демо-сайт  →  3 Скрины  →  4 Вычитка  →  5 Страница КП  →  6 PDF  →  7 Проверка
                                                                                    ↘ 8 продукт (другой репо, когда удобно)
```

| # | Этап | Модель | Почему |
|---|---|---|---|
| 1 | Текст КП для салонов (с местами под скрины) | **Claude Opus 5.5** | Русский продающий текст + следование брифу |
| 2 | Правки демо-сайта (тексты + цвета + кликабельность) | **Claude Sonnet 5.5** | Точечные правки в коде; демо должно выглядеть «готовым к скрину» до этапа 3 |
| 3 | Наглядные скрины процесса | **Composer 2.5 Fast** | Playwright-скрины дашборда + макет карточки YClients; механическая работа |
| 4 | Вычитка текста и подписей к скринам | **GPT-5.6 Sol** | Другая модель — свежий взгляд владельца, не защищает свой текст |
| 5 | Мобильная страница КП с визуалами | **Claude Opus 5.5** | Вёрстка + дизайн + вставка скринов |
| 6 | PDF из страницы | **Composer 2.5 Fast** | Скрипт печати |
| 7 | Финальная проверка | **Gemini 3.8 Flash** | Дёшево смотрит скриншоты и стоп-лист |
| 8 | Ярлыки «Спящие» (рабочий дашборд) | **GPT-5.6 Sol** | Логика API; не блокирует КП |

## Этап 1. Текст КП для салонов

**Модель:** Claude Opus 5.5  
**Вход:** `docs/kp/brief.md`  
**Выход:** `docs/kp/salon.md`  
**Следующий этап ждёт:** готовый `salon.md` с плейсхолдерами V1–V4

**Промпт:**

```text
Задача: написать текст коммерческого предложения «AI-маркетолог» только для салонов красоты.

Прочитай docs/kp/brief.md целиком. Косметологию и clinic.md не трогай и не создавай.

Результат: docs/kp/salon.md.

Требования:
- Структура строго по разделу «Структура КП (салоны)» в брифе.
- Первый экран: «Кто реально приносит прибыль вашему салону?» + одна строка боли + демо и контакты.
- В местах из таблицы «Визуалы» вставь markdown-плейсхолдеры:
  ![V1: сводка собственника](visuals/v1-summary.png)
  ![V2: список на обзвон](visuals/v2-call-list.png)
  ![V3: ярлык в карточке YClients](visuals/v3-yclients-label.png)
  ![V4: выгрузка Excel](visuals/v4-excel.png)
  Под каждым — одна строка подписи простым языком (как в брифе).
- Слова только из словаря «салоны». Ничего из «Убрать / не писать». Гелиосити — нигде.
- Кейс только Sisters, Уфа; не выдавай его за правду для всех.
- Короткие блоки (1–3 предложения): читают с телефона.
- Тон: «делаем так», без «если вы хотите».
- Цены и оплата — из брифа. Подписи «Стоимость» и «Срок».
- Разметка: ## для блоков (потом соберём страницу).

В конце ответа: список мест, где не уверен в формулировке.
Код и картинки не трогай.
```

## Этап 2. Правки демо-сайта (перед скринами)

**Модель:** Claude Sonnet 5.5  
**Вход:** `docs/kp/brief.md`, `docs/kp/salon.md` (чтобы тон и цены совпали с КП)  
**Выход:** обновлённые `src/main.ts`, `src/tour.ts`, `src/charts.ts`, `src/dashboard.ts` (+ стили при необходимости)  
**Следующий этап ждёт:** `npm run build` ок; дашборд готов к скриншотам (различимые цвета, подсказка про клик)

**Промпт:**

```text
Задача: привести демо-сайт в вид, с которого можно снимать скрины для КП.

Прочитай docs/kp/brief.md и docs/kp/salon.md. Тексты лендинга и цены должны совпадать по смыслу с КП
(не копируй КП целиком — сайт остаётся короче). Логику дашборда не ломай.

Правишь: src/main.ts (renderPage, METHOD_SEGMENTS, форма), src/tour.ts (тексты шагов),
src/charts.ts, src/dashboard.ts. При необходимости — src/style.css.

Обязательные правки:
1. Hero: название продукта + вопрос «Кто реально приносит прибыль вашему салону?» + строка про диагностику базы.
2. Заметный блок про автоматические ярлыки в YClients (сильная сторона №1 брифа) выше «Как это выглядит в работе».
3. Раздел данных:
   - локально: база не уходит в интернет — защита от утечки;
   - «Интеграция с YClients» вместо «только чтение / токены»;
   - границы: «Не заменяет CRM и не рассылает сообщения»;
   - дубли: «Убираем дубли: один гость с разных филиалов или 8… и +7… — один клиент»;
   - аккордеон «Как считаются группы» (не «для тех, кто хочет копать») — давность, частота, сумма + настройка под салон.
4. «Ядро» при первом упоминании: «Ядро — постоянные клиенты».
5. Форма: «Внедрение от 50 000 ₽, точная цена после оценки базы»; необязательное поле «Примерно клиентов в базе»
   (Formspree + Telegram-черновик).
6. Ритм работы, пункт про ярлыки: «Группы автоматически проставляются в карточках YClients».
7. Цвет «Новичков» в charts.ts заметно отличить от «Ядра» (не фиолетовый, не неон); синхронизировать, если цвет есть ещё где-то.
8. Подпись у сегментов дашборда: «Нажмите на группу, чтобы открыть список клиентов» + cursor: pointer.

Проверка: npm run build; открой /#dashboard — цвета групп различимы, клик по группе открывает список,
тур доходит до конца. Кратко перечисли, что изменил (для этапа 3).
```

## Этап 3. Наглядные скрины процесса

**Модель:** Composer 2.5 Fast  
**Вход:** бриф (раздел «Визуалы»), `docs/kp/salon.md`, результат этапа 2 (актуальный демо-сайт)  
**Выход:** `docs/kp/visuals/v1…v4*.png` + `docs/kp/visuals/manifest.md`  
**Следующий этап ждёт:** 4 файла картинок и манифест с подписями

**Промпт:**

```text
Задача: собрать 4 наглядных кадра для КП — процесс в привычном интерфейсе (панель + YClients).

Прочитай:
- docs/kp/brief.md → раздел «Визуалы»
- docs/kp/salon.md → плейсхолдеры V1–V4 и текущие подписи
- кратко посмотри src/dashboard.ts / демо, чтобы знать, куда кликать

Сделай папку docs/kp/visuals/ и файлы:

V1 — сводка собственника:
  npm run build && npm run preview; Playwright: открыть /#dashboard, вкладка сводки,
  скрин области с долями групп/выручки → visuals/v1-summary.png (ширина ~1200px, без лишнего хрома браузера по возможности).

V2 — список на обзвон:
  клик по группе (например «Уходят» или список «без будущей записи»), скрин таблицы/списка клиентов
  → visuals/v2-call-list.png. На скрине только демо-данные.

V3 — ярлык в карточке YClients:
  Приоритет A: если в проекте или у пользователя есть обезличенный скрин карточки YClients с ярлыком группы —
  положи как visuals/v3-yclients-label.png.
  Приоритет B (если A нет): сделай статичный HTML-макет «карточка клиента как в YClients»
  (узнаваемые отступы/ярлык-чип с названием группы, вымышленное имя вроде «Анна К.» без телефона),
  отрендерь в PNG через Playwright → visuals/v3-yclients-label.png.
  Не копируй логотип/бренд YClients дословно, если это риск; достаточно «привычной карточки CRM салона»
  с подписью в манифесте: «Так группа появляется в карточке клиента в YClients».

V4 — Excel / выгрузка:
  скрин кнопки выгрузки и/или фрагмента списка с действием Excel → visuals/v4-excel.png.

Манифест docs/kp/visuals/manifest.md:
| ID | Файл | Что на кадре | Подпись для КП (1 строка) | Источник |
Для подписей сверься с salon.md; при необходимости предложи более понятную подпись.

В salon.md картинки пока не вшивай бинарно — только убедись, что пути плейсхолдеров совпадают с реальными файлами.

Проверка: все 4 PNG существуют, открываются, на них нет реальных телефонов клиентов.
```

## Этап 4. Вычитка текста и подписей к скринам

**Модель:** GPT-5.6 Sol  
**Вход:** бриф, `docs/kp/salon.md`, `docs/kp/visuals/manifest.md` (+ сами PNG при сомнении)  
**Выход:** обновлённые `docs/kp/salon.md` и `docs/kp/visuals/manifest.md`  
**Следующий этап ждёт:** вычитанный текст, готовый к вёрстке

**Промпт:**

```text
Ты — собственница сети салонов, бывший мастер. Маркетинговые термины не знаешь.
Читаешь КП с телефона; на первый экран — 3 секунды. Хочешь видеть, «как это выглядит», на знакомых экранах.

Прочитай:
- docs/kp/brief.md (стоп-лист и структура)
- docs/kp/salon.md
- docs/kp/visuals/manifest.md
- при необходимости открой PNG из docs/kp/visuals/

Сделай:
1. Что понятно за 3 секунды на первом экране? Если не ясно «что это и зачем мне» — это ошибка №1.
2. Все слова, которые бывший мастер переспросит.
3. Всё из стоп-листа брифа + любое «Гелиосити» / косметология / пациенты.
4. Места с «можем так или так» вместо «делаем так».
5. Где кейс Sisters выдаётся за правду для всех.
6. По каждому V1–V4: понятна ли подпись без объяснений? Совпадает ли картинка с обещанием в тексте рядом?
   Если подпись канцелярская — перепиши по-человечески в salon.md и в manifest.md.

Сначала таблица «Место → Проблема → Как исправить», потом внеси правки в salon.md и manifest.md.
Структуру блоков и набор V1–V4 не меняй. Код не трогай. Новые скрины не снимай — только текст и подписи.
```

**Вход:** вычитанные `docs/kp/salon.md`, `docs/kp/visuals/*`, бриф; палитра сайта

```text
После: ~/.cursor/skills/kill-ai-slop/SKILL.md

Сделай:
- offer/salon.html — текст один в один из salon.md (не переписывай формулировки).

- Подключи страницу как доп. вход в vite.config.ts (build.rollupOptions.input).
- src/main.ts и логику дашборда не трогай.

  (на мобиле на всю ширину колонки, с лёгкой рамкой/фоном, без «карточного ада»).

- @media print под A4: без лишней навигации, не резать скрин посередине (break-inside: avoid).
- og:title / og:description для шаринга в мессенджере.

Проверка: npm run build; открой /offer/salon.html на 375 и 1440; приложи скриншоты первого экрана
и блока с V3 (ярлык). Кратко опиши, куда положил картинки.
```

## Этап 8. Доработка продукта (не блокирует КП)

**Модель:** GPT-5.6 Sol  
**Где:** репозиторий рабочего дашборда Sisters, не этот демо-сайт  
**Когда:** после отправки КП или параллельно с этапами 5–7

**Промпт:**

```text
Задача: ручной ярлык «Спящие» в YClients важнее расчётной группы «Уходят».

Проблема: администратор позвонил, клиент переехал, вручную поставили «Спящие»;
в следующей выгрузке человек снова в «Уходят» — повторные звонки.

1. По API YClients и нашему коду: автоярлык заменяет старый или добавляет второй?
2. Правило: ручной «Спящие» → не попадает в обзвон «Уходят»; автозапись ярлык не перезаписывает.
3. Как отличить ручной ярлык от автоматического — предложи по п.1.
4. Тесты на эти случаи.

Отдельно (только исследование): вкладка «Переходы» считает только месяц к месяцу —
как сделать произвольные периоды и какой объём работы.
```
